# CLAUDE.md

Instructions for Claude Code (or any agent) working in this repository.

## Repository map

- `infra/bootstrap/` — Terraform root for the GCS state bucket and the billing budget. Applied once, local state, never destroyed by anything in `infra/`.
- `infra/` — Terraform root for everything billable or app-specific: VPC, firewall, compute instance, Identity Platform, Workload Identity Federation, Secret Manager, `vm-assets` bucket. Remote state in the bootstrap bucket.
- `infra/scripts/startup.sh.tpl` — idempotent per-boot provisioning script rendered into instance metadata. `infra/scripts/ecosystem.config.js` is inlined into it at apply time.
- `web/` — Next.js 16 app (App Router, TypeScript, Vitest). `web/CLAUDE.md` includes `web/AGENTS.md`, auto-generated by `next dev` — read `node_modules/next/dist/docs/` before writing Next.js code; this version differs from training data.
- `ops/` — `vm-start.sh` / `vm-stop.sh`, the only supported way to start/stop the VM.
- `.github/workflows/` — `ci.yml` (PR checks + infra IAM guardrails), `release.yml` (release-please), `deploy.yml` (called by `release.yml` on release; also `workflow_dispatch`), `build-oqsprovider.yml` (manual, builds the PQC provider).
- `docs/` — reference documentation, in Brazilian Portuguese. `README.md` (root) holds the quickstart and the OWASP Top 10 mapping. `prd.md` holds the course requirements.

## Starting / stopping `app-vm`

**Never run `gcloud compute instances start/stop app-vm` directly, and never run raw `gcloud compute addresses create/delete` for it either.** Always use:

```bash
./ops/vm-start.sh   # reserves a static IP, attaches it, starts the instance
./ops/vm-stop.sh    # stops the instance, detaches and releases the static IP
```

**Why:** `infra/compute.tf` intentionally declares an **ephemeral** external IP, not a reserved one (a reserved address was tried and reverted — see `docs/free-tier.md`). GCP bills a reserved static IP whenever it isn't attached to a *running* instance. Reserving one only for the window the VM is up, and releasing it the moment it's stopped, is the only way to get a stable public IP while the VM is on **and** stay within the Always Free tier while it's off. Starting/stopping without these scripts either leaves a static IP billing or leaves the instance without the expected access-config.

Both scripts read `project_id`/`region`/`zone` from `infra/terraform.tfvars` (gitignored). **Never hardcode the GCP project ID in a committed file** — this repository is public per the course requirements. The same applies to `infra/backend.tf`: the state bucket name (which embeds the project ID) is supplied via the gitignored `infra/backend.hcl` at `terraform init -backend-config=backend.hcl` time.

**Drift note:** while the VM is running via `ops/vm-start.sh`, its access-config points at a reserved IP that Terraform doesn't know about. Running `terraform apply` on `infra/` while the VM is up swaps it back to ephemeral (harmless — `ops/vm-stop.sh` would have released the reservation anyway — but the IP changes). Prefer `ops/vm-stop.sh` before applying.

## Secrets and identity

- The Identity Platform API key lives only in Secret Manager (`infra/secrets.tf`). The app reads it at runtime via `web/lib/gcp/secret.ts` with the VM's service account. Do not reintroduce it as a GitHub secret, an `.env.production` entry, or a build-time env var. `deploy.yml` writes only `NODE_ENV`, `PORT`, `GOOGLE_CLOUD_PROJECT` to `/opt/app/.env.production`.
- The deploy service account (`infra/wif.tf`) must hold no predefined project-level role — only instance-scoped `roles/compute.instanceAdmin.v1` + `roles/iap.tunnelResourceAccessor`, `roles/iam.serviceAccountUser` on the VM's SA, and the read-only custom role `deployVmOperator`. `ci.yml`'s "infra IAM & firewall guardrails" job fails the PR if this changes; do not weaken those checks to make a PR pass.
- No SSH key is stored in GitHub. Deploy reaches the VM through `gcloud compute ssh/scp --tunnel-through-iap` with an ephemeral key. The VM sets `block-project-ssh-keys = "TRUE"`; never add keys to project metadata.

## Releases and deploy

- Versioning is automated by release-please. **Never edit `version` in `web/package.json` or `web/CHANGELOG.md` by hand.** Use Conventional Commits: `feat:` → minor, `fix:` → patch, `feat!:`/`BREAKING CHANGE:` → major; `docs`/`test`/`chore`/`style` don't bump.
- A plain push to `main` does not deploy. Only merging the `chore(main): release X.Y.Z` PR (which creates the tag + GitHub Release) triggers `deploy.yml`. `workflow_dispatch` on the `Deploy` workflow forces a redeploy of current `main`.
- The app is built in GitHub Actions as a `next build` standalone bundle. Never build on the VM (`e2-micro`, 1 GB RAM).

## Conventions for `web/`

- `npm run lint`, `npm run typecheck`, `npm test` and `npm run build` run without credentials; CI runs the first three on every PR. Run them before committing.
- Route handlers are split into `route.ts` (Next.js wiring) and `handler.ts` (pure logic with injected dependencies, unit-tested in `route.test.ts`). Keep new API logic in that shape.
- Forms are plain HTML `<form>` submissions, no client-side JavaScript. API routes redirect (`303`) rather than returning JSON to the browser; field-level failures go back to the same page with `?error=...`, everything else to `/error?reason=...`.
- Rate limiting is an in-process `Map` (`web/lib/security/rate-limit.ts`) by design — single VM, no database. Do not add a database or a shared store for it.
- Every provider rejection collapses to a single generic response (no account enumeration). Preserve that in any new auth flow.

## Docs

- `docs/` and `README.md` are written in Brazilian Portuguese; code comments, commit messages and this file are in English. Keep that split.
- Do not link to `.specs/` from committed files — that directory is gitignored (local planning artefacts) and links to it are dead in the public repo.
- When you change behaviour in `infra/scripts/startup.sh.tpl`, `deploy.yml` or the auth flow, update the matching section in `docs/` (`architecture.md` stage list, `application.md` CI/CD table, `security.md`, `troubleshooting.md`) in the same commit.

## Real-deployment corrections worth knowing before touching `infra/scripts/startup.sh.tpl` or `deploy.yml`

Bugs found only by applying this against a live GCP project — not visible from reading the Terraform alone. All are fixed in the committed script + `deploy.yml`; listed here so a future edit doesn't reintroduce the pattern. Details in `docs/troubleshooting.md`.

1. Ubuntu 24.04's systemd unit for SSH is `ssh.service`, not `sshd.service`. `systemctl reload sshd` fails and (under `set -euo pipefail`) kills the entire startup script silently.
2. The HTTPS Nginx server block embeds the current public IP into its `ssl_certificate` path at creation time. The idempotency guard must check that the file's embedded IP still matches the current public IP — not just that the file exists — or an IP change (e.g. after a stop/start cycle) leaves Nginx pointing at a stale, non-existent cert path.
3. `/opt/app/ecosystem.config.js` must be written **unconditionally** on every boot, not behind a `[ ! -f ]` guard. A VM first provisioned with an early version of the file (which ran `pm2 start npm -- start`) kept that stale copy through every later `terraform apply` + reboot; the first real CI deploy then crash-looped on `ENOENT /opt/app/package.json` and Nginx served 502. `deploy.yml` also scp's this file on every deploy, and the PM2 reload is `pm2 delete` + `pm2 start` (not `pm2 reload`, which keeps a running app's cached script/interpreter args).
4. `next build` nests the standalone output under `.next/standalone/web/` because the app is in the `web/` workspace — `server.js`, its `node_modules`, and its `.next/` are all one level down, and `.next/static` / `public/` are not copied in at all. `deploy.yml`'s assemble step takes `.next/standalone/web` as the archive root and re-adds static/public; a naive `cp -r .next/standalone/. bundle/` puts `server.js` at `bundle/web/server.js` and PM2 fails with `Script not found: /opt/app/current/server.js`.
5. The Nginx reverse-proxy `location /` must forward `X-Forwarded-Proto` (and `X-Forwarded-Host` / `X-Forwarded-For`). `proxy.ts` builds its same-origin / CSRF comparison from `request.nextUrl` — without `X-Forwarded-Proto: https` Next assumes `http://` and every `POST /api/auth/*` 403s because the browser `Origin` is `https://`. `X-Forwarded-For` also feeds the rate limiter's client-IP resolution. The stage-10 vhost rewrite guard re-fires on a proxy vhost missing `X-Forwarded-Proto`, so rebooting upgrades an older VM.
6. `systemctl reload nginx` does not activate a newly installed OpenSSL provider (`oqsprovider`): workers fork from a master whose OpenSSL state predates the provider, while `nginx -t` (a fresh process) passes. Stage 8b uses `systemctl restart nginx`. Any change to the set of active OpenSSL providers needs `restart`, not `reload`.
7. Building `liboqs` on the `e2-micro` at boot does not finish in reasonable time. The provider is built by `.github/workflows/build-oqsprovider.yml` (`ubuntu-24.04` runner, same glibc) and uploaded manually to the private `vm-assets` bucket; stage 8b downloads it with an OAuth token from the metadata server via `curl`, not via the snap `gcloud`. `liboqs` and `oqs-provider` versions are coupled — check the provider's `RELEASE.md` for the matching `liboqs` tag.
